# 亚马逊选品 · 两层框架 RAG Demo

把你给的「第一层 市场容量与需求 / 第二层 竞争格局」经验框架，做成一个**能跑、能测、能追问**的 demo：

1. **规则评分引擎** — 把 12 条经验阈值变成可计算规则，输入卖家精灵数值，输出分层得分、否决线与下一步动作。
2. **中文 BM25 RAG** — 知识库按小节切分检索，问答时先检索再生成；有 `ANTHROPIC_API_KEY` 时由 Claude 流式归纳，没有时降级为「检索结果直出」，**零配置可跑**。

零 npm 依赖，只用 Node 内置模块。

## 跑起来

```bash
cd E:\code\amazon-market-rag
npm start
```

打开 http://localhost:8787

默认是纯检索模式。要启用 LLM 生成：

```bash
set ANTHROPIC_API_KEY=sk-ant-...   # Windows cmd
npm start
```

模型固定为 `claude-opus-5-5`，开启 adaptive thinking，并默认带上服务端 fallback（`fallbacks: "default"`，beta `server-side-fallback-2026-07-01`）；若账号不支持该 beta，会自动去掉后重试一次。

## 两种运行模式

同一份前端代码，两种环境下跑：

| | 本地模式 | 静态模式（GitHub Pages） |
|---|---|---|
| 启动 | `npm start` | 推送到 `main`，Actions 自动构建部署 |
| 市场体检 | ✅ 完整 | ✅ 完整 |
| 检索试玩 | ✅ 完整 | ✅ 完整 |
| 知识问答 | ✅ Claude 流式 | ⚠️ 纯检索直出（API key 不能进仓库） |
| 知识库来源 | 服务端实时读 `kb/` | 构建时预生成 `kb.chunks.json` |

实现上 `src/scorer.js`、`src/retriever.js`、`src/answer.js` 都是**零 import 的纯 ESM**，浏览器和 Node 跑的是同一份代码；服务端通过在 HTML 里注入 `<meta name="demo-mode" content="server">` 告诉前端自己在线，静态版没有这个标记就自动降级。所以本地和 Pages 的评分、检索结果逐字节一致。

## 部署到 GitHub Pages

```bash
node scripts/build-static.mjs   # 本地预览静态产物 → site/
```

推送到 `main` 后，`.github/workflows/deploy-pages.yml` 会自动跑测试、构建 `site/` 并发布。仓库里 `site/` 已被 `.gitignore` 忽略，Pages 上的是 Actions 现场构建的，不会和 `kb/` 脱节。

首次需要手动开一次 Pages（Settings → Pages → Source 选 `GitHub Actions`）。

## 三个页签

| 页签 | 作用 |
|---|---|
| **市场体检** | 选示例市场或手填 14 个指标 → 分层得分、每条规则的通过/需论证/不利、依据小节、动作建议 |
| **知识问答** | 流式问答，答案带 `[S#]` 引用编号，底部列出命中片段 |
| **检索试玩** | 直接看 BM25 命中了哪些片段及得分，用来验证检索质量 |

## 评分规则

每条规则三档：`pass`（1 分）/ `warn`（0.5 分）/ `fail`（0 分），参考项（类目月总容量）不计分。

**第一层**

| 指标 | 健康线 | 来源 |
|---|---|---|
| 核心词月搜索量 | ≥ 10,000；< 10,000 否决 | 原文 |
| 核心词月增长率 | > 10% | 原文 |
| TOP100 月均销量 | 600—3,000；< 600 不利，> 3,000 需论证 | 原文 |
| 新品进榜数量与占比 | ≥ 5 个且 ≥ 10%；占比 < 10% 否决 | 原文 |
| 中位数 / 均值 | 见第二层 | — |

**第二层**

| 指标 | 健康线 | 来源 |
|---|---|---|
| 前三品牌集中度 | ≤ 30%；> 40% 否决 | 原文给 40%，30% 已确认 |
| Top10 销量集中度 | < 45%；> 60% 头部效应 | 原文给「近 6 成」，45% 已确认 |
| Top20 平均评论数 | ≤ 800 新手可切入；≥ 10,000 壁垒极高 | 原文 |
| 点击集中度 | < 40% 有自然空间；> 60% 自然位锁死 | **已确认**，原文只给方向 |
| 市场平均评分 | ≤ 4.3 有改进空间；> 4.7 需显著创新 | 原文 |
| 中位数 / 均值 | ≥ 0.6 分布均匀，< 0.35 头部拉动型 | **已确认**，原文只要求「先看中位数」 |

> **原文** = 你的框架里写明的数字；**已确认** = 原文只给了方向、demo 补的档位，你于 2026-11-18 确认沿用。目前所有阈值都已有明确来源，没有待确认项。
>
> 30% 这条缓冲带的理由：品牌集中度是工具按「同品牌多链接归属」算的估算值，在估算值上不宜设 39.9% 通过 / 40.1% 否决的悬崖边界。
>
> UI 里每条规则旁都有来源标注，`test/run.js` 里有两条测试专门守着：标注「原文」的阈值数字必须确实写在知识库里；规则的标注必须与其阈值的真实来源一致（这条是回归测试，曾经混合标注被硬编码成「原文+自定」，导致补档已确认后仍显示待确认）。

所有阈值集中在 `src/scorer.js` 顶部的 `THRESHOLDS` 对象，每条带 `src` 和 `note` 说明来自原文哪句话。**改口径只改那一处**，规则逻辑和测试会跟着走。

**判定**：命中否决线或第一层 < 60% → `reject`；第二层 < 50% → `risky`；有不利项或需论证项 ≥ 3 → `conditional`；其余 → `go`。

## API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/markets` | 示例市场 + 规则清单 + 生成模式 |
| POST | `/api/score` | body `{metrics}` → 评分结果 |
| POST | `/api/ask` | body `{question}` → SSE 流（`delta` / `done`） |
| GET | `/api/search?q=&k=` | 纯检索，返回 BM25 命中 |
| GET | `/api/kb` | 片段清单 |

## 已知边界

- 检索是词项匹配（BM25），不是语义检索。「矫姿」和「坐姿」这类近义词若不在同义词表里就匹配不到——要换语义检索需要嵌入模型， demo 刻意避开了这个依赖。
- 销量数字全部来自工具估算：头部 ASIN ±30%、腰部以下可能超 50%。评分只做门槛判断，不做 ROI 测算。
- 前端深色模式跟随系统设置，没有手动切换。
